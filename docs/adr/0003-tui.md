# ADR 0003 — TUI instead of a web GUI (sketch)

- **Status:** Built (v1) — 2026-09-04
- **Decision:** Build a **terminal UI (TUI)** as the primary interface instead of the
  web console. Framework: **Python Textual** (attractive, app-like) — following the
  requirement "attractive and genuinely usable". **whiptail** (bash) is kept as a
  zero-dependency **fallback** (`tui --simple`). The web GUI (api/web) is frozen as a
  reference.
- **Supersedes the direction in:** the web onboarding rewrite (paused in BACKLOG).

## Framework choice: Textual (primary), whiptail (fallback)
The first sketch was whiptail (zero install), but "attractive and genuinely usable"
raises the bar above whiptail's ceiling (square dialogs, one at a time). **Textual**
gives an app feel: tabs, stat cards, DataTables, forms on ONE screen, live log, a
dark theme (TCSS). It requires a small venv (`textual`) — built by `install.sh`
(the same pattern as the api venv). Go/bubbletea was considered but Go is not
present on the host. The whiptail path remains for hosts without Python/venv.

## Why whiptail
- **Zero extra install** — present on essentially every Debian/PVE host
  (`/usr/bin/whiptail`, package `whiptail`). Fits the ethos "self-contained, for
  people without a PBS machine".
- **Matches the bash CLI** — the TUI is just another frontend; it *shells out* to the
  same `lxc-offsite` commands (lock/preflight/audit reused for free), and reads data
  via `lxc-offsite --json`.
- **SSH-friendly** — runs where you administer the host anyway. `dialog`/`fzf` are
  not present on the host → avoided.
- Alternative if an app feel is wanted later: Python **Textual** (richer live
  dashboard, but requires pip/venv). Noted, not chosen.

## Priority (the user's focus)
1. **Simple restic setup** (repo/sftp/password/init) — highest
2. **Export the DR key** (future restore)
3. **Backup — all or a single guest**
4. **Restore**
5. Metrics & other — included, but lower focus

## Screen map
```
Main menu
├─ 1. Setup / onboarding (restic)      ← wizard: engine→mode→sftp→password→init
├─ 2. Back up                          → [All protected] / [Select guest…]
├─ 3. Restore                          → guest → snapshot → new vmid → storage → run
├─ 4. Export DR key                    → warning → repo URL + password (textbox/file)
├─ 5. Status & metrics                 → last run, offsite size, snaps, verify
├─ 6. Maintenance                      → prune (dry→real) / verify / test-restore
└─ 0. Exit
```

## Architecture
- `lib/tui.sh`, a new dispatcher subcommand **`lxc-offsite tui`**.
- The TUI **calls the CLI** (`"$LXCO_BIN" --json <cmd>` for data, `"$LXCO_BIN" <cmd>`
  for actions) → no duplicated business logic, the same envelope the web UI used.
- No state of its own; config is written to `/etc/lxc-offsite/config` (secrets to
  `RESTIC_PASSWORD_FILE` 0600 + a pointer in your password manager).
- `lxc-offsite tui --selftest` — a non-interactive wiring check (no TTY required).

## Status
Skeleton built (main menu + setup wizard + backup/restore/export/status/maintenance
wired to the CLI). Requires a TTY to run interactively. Remaining: fine-tune the
forms, error handling, the metrics panel, and connect the setup write to the real
config only after the user's go-ahead.
